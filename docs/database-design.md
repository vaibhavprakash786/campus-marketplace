# MongoDB logical model

Conventions: `_id: ObjectId`, `createdAt/updatedAt: Date`, references ObjectId, `status` enum; all prices integer paise (INR), positive for offers/listings; timestamps in UTC. Use schema validation and service-level authorization. Public DTOs omit email, passwordHash, verification evidence. Soft deletion preferred for audit-related records.

## Verification details and administrator audit logs
`users.verificationMethod` is one of `college_email/manual_review/sso` when set. Store `verificationRequestedAt`, `verifiedAt`, `verificationReviewedBy` (admin ObjectId, for manual review), `verificationDecisionReason` (private), and a private `verificationEvidenceRef` only when needed. `verificationStatus` transitions: `unverified/rejected -> pending`, `pending -> verified/rejected`, and admin revocation `verified -> unverified`. Token hashes/challenges must be expiring and single-use (separate secure ephemeral records if needed); never store plaintext tokens. For SSO, use a unique scoped provider subject and validate student eligibility; credential model is to be decided with the institution. Verification decisions and revocations are audited. Only authorized reviewers access evidence and reasons.

**Eighth collection: `audit_logs` (MVP).** Append-only administrator-action audit trail. Required: `_id:ObjectId`, `actorId:ObjectId(users)`, `action:String` (enum e.g. `verification.approve`, `verification.reject`, `verification.revoke`, `user.suspend`, `user.reinstate`, `listing.remove`, `report.update`, `transaction.resolve`), `targetType:String`, `targetId:ObjectId`, `outcome:'success'`, `requestId:String`, `createdAt:Date`. Optional: `metadata:Object` (strict allowlist, sanitized non-sensitive field changes), `reasonCode:String`. Indexes: `(actorId,createdAt desc)`, `(targetType,targetId,createdAt desc)`, `(createdAt desc)`, and unique `(requestId,action,targetType,targetId)` where request ID uniquely identifies an attempted operation. Only authorized audit reviewers may query; students and ordinary moderators cannot read by default. No update/delete endpoints; protect retention/backups and avoid logging secrets/evidence/message bodies. Successful admin state change and audit insertion must commit atomically; denial/failed-attempt telemetry belongs to separate security logs. No TTL until approved retention policy.

**Offer indexes and invariants:** enforce unique partial `(conversationId)` where `status='pending'`; `parentOfferId` must reference the current pending offer in the same conversation and belong to the opposite proposer. `pending -> accepted/rejected/countered/withdrawn/expired` only, never reopen; all history retained. Buyer starts, seller may counter; alternating participants may counter; recipient alone accepts/rejects, proposer alone withdraws. `acceptedOfferId` must be unique in transactions. Pending offers for *other* conversations on the same listing are expired on successful acceptance. A pending offer may expire by policy without modifying a historical accepted offer.

## Validation
- Normalize email; constrain text lengths and graduation year to sensible configured bounds; no plaintext passwords; role defaults student and cannot be self-promoted.
- Image count and file limits configurable; validate Cloudinary public IDs as owned assets, do not trust submitted URLs.
- Conversation participants distinct, seller must equal listing seller, buyer cannot be seller; unique compound index prevents duplicate creation races.
- Messages max length, nonempty trimmed, no unbounded embedded message arrays; use cursor pagination on `(createdAt,_id)`.
- Offers amount positive safe integer, parent offer must be in same conversation, new counter creates a new offer and changes predecessor `pending -> countered`; never overwrite history.
- One actionable pending offer per conversation (service rule; optionally partial unique index `conversationId,status=pending`); responding must match expected pending status and authorized recipient.
- Only one reserved transaction per listing (partial unique index). Listing `reservedTransactionId` points to winning transaction. Status invariants: available has null reservation; reserved points to reserved transaction; sold points to completed transaction (retain reference); removed cannot be reserved.
- Reports reject invalid targets and self-reports, enforce reasonable report-rate limits.

## Reservation and transaction state machine
`available -> reserved -> sold` on successful handover; `reserved -> available` on cancellation/expiry; `available -> removed`; `reserved -> disputed` is transaction status only and listing remains reserved pending resolution. `sold` is terminal for MVP. Admin moderation may remove an available listing; handling a reserved listing requires cancelling its transaction atomically first.

Accepted offer creates a reserved transaction; only if listing conditional update matches `status=available`. In one MongoDB transaction: check pending offer, update offer to accepted, set competing pending offers to expired, insert reserved transaction, set listing to reserved with transaction ID. Unique partial transaction index provides a second guard. On write conflict/duplicate key return `409`, not success. Offer accept and transaction creation must be idempotent by acceptedOfferId (unique index recommended). Expiry worker or request-time reconciliation uses conditional `status=reserved` and `expiresAt <= now` with listing update in a transaction; TTL deletion must NOT delete transaction history. Confirmation requires both timestamps and commits `transaction.status=completed` and `listing.status=sold` together. Cancellation similarly updates both. Persist disputes; never complete on one confirmation.

MongoDB multi-document transactions require a replica set or sharded deployment. Ensure indexes exist before accepting writes; handle transient transaction retries carefully and use idempotency keys for client retries. Atomic single-document compare-and-set guards every state transition; transactions preserve cross-collection consistency.


## Stage 2 implemented storage boundary
The implemented `users` schema includes email, passwordHash (select:false), name, department, graduationYear, role, verificationStatus, status and optional verificationMethod/verifiedAt. The `sessions` collection stores userId, SHA-256 hash of a cryptographically random opaque token and expiresAt (TTL index). TTL cleanup is not a substitute for request-time expiration checks. Verification evidence, challenges, audit logs, password reset records and reviewer decision fields remain **design only**, pending institutional method approval. No verification status changes are exposed through student endpoints.


### Stage 2 email_verifications implementation
`email_verifications`: `userId:ObjectId` (required, unique ref users), `codeHash:String` (required SHA-256 of user ID and random six-digit OTP), `expiresAt:Date`, `resendAfter:Date`, `attempts:Number` (0–5), timestamps. TTL index on `expiresAt`; expiry checked explicitly on every verification attempt. No plaintext OTP persisted. Successful verification deletes challenge before updating user status; for strict atomicity across a process crash, use a MongoDB transaction on a replica set before production.

## Stage 3 implemented listings storage
`Listing` is defined in `apps/api/src/modules/listings/model.ts`. Required: `sellerId` (immutable users ObjectId), trimmed `title` (3–120), `description` (5–5000), `category` (1–60), `condition` (`new/like_new/good/fair/poor`), `pricePaise` (positive safe integer), `location` (2–120), and `status` (`available/reserved/sold/removed`, initially `available`). `imageAssets` defaults to an empty array and cannot be supplied/modified through Stage 3 endpoints. Optional future-stage fields `reservedTransactionId` and `removedReason` are stored but not client-writable. Timestamps use Mongoose `timestamps: true`.

Indexes implemented: `(status, createdAt desc, _id desc)` for available marketplace pagination and `(sellerId, createdAt desc, _id desc)` for owner pagination. Only available listings appear in general browse/detail; owner list includes archived listings. Deletion atomically transitions `available -> removed`, preserving history. Editing is limited to `available` listings, with atomic status/owner predicates. Category remains a bounded free-form label because Stage 0 left the allowed-category taxonomy configurable and unapproved; no category enum is invented. Stage 3 uses bounded offset pagination (`page` 1–10000, `limit` 1–50); future-stage search/cursor pagination is not implemented.
